# 面试准备：六标准对照（2026-10-31）

对照业界对 Agent 项目的六条评判标准（真实业务 / 后端工程 / 自主规划 / 上下文工程 /
可观测 / 人机协同）做的诚实自评，附每条的面试口径。定位清单（[定位与减法清单.md](定位与减法清单.md)）
回答"投什么、不投什么"，本文回答"被追问时怎么答"。**只做叙事准备，不为补短板开新工程。**

## 总评

- **误区检测**：不是"LLM + Prompt + 工具 + 网页"的套壳项目——没有演示页面那层皮，
  取而代之的是状态机、审批边界、审计链。真实风险是镜像误区：**工程密度高、业务故事弱**，
  三句话讲不清"解决谁的什么问题"。对策见 README 前屏的关键词索引与对外一句话。
- **强项**：可观测（论点级）、人机协同（论点级）、后端工程体系。
- **部分达标**：真实业务（靠 dogfood 台账支撑）、自主规划（靠"确定性优先"立场支撑）。
- **已知薄点**：上下文工程（只准备口头答案，不开新工程）。

## 逐条口径

### 标准一：真实业务问题 —— 部分达标，最大风险点

**事实**：业务是"受治理的仓库交付"，用户是维护真实仓库的开发者；dogfood 台账
（ADR-033 预注册：连续 10 个真实交付或 4 周）是可量化的效果指标；乱码事件
（验收记录 §6.7）是真实的检测缺口暴露。

**必问"除了你自己还有谁用"**：答"当前是单用户 dogfood，这是刻意的——评测型工作的
第一原则是先在自己身上获得真实负样本，再谈泛化；台账的计数规则是预注册的，空泛的
'多租户'宣称反而是我避免的"。不编造外部用户。

### 标准二：后端工程体系 —— 达标，唯一薄点是并发

**事实**：Postgres MergeStore（head-SHA 乐观锁）、审计 WAL 哈希链、CLI/HTTP 入口、
审批边界 519 行测试加固、failed / needs_human / infra_error 完整状态分类。

**被问并发**：答"单操作者是当前边界；但设计里已为多写者留了位置——head-SHA 乐观锁
防并发合并覆盖，审计链按写入者分段，冲突时宁可失败也不静默覆盖"。

### 标准三：自主规划 —— 部分达标，主动定调"确定性优先"

**事实**：交付 Agent 是有界循环——实现 → 确定性验证 → 带 feedback 的修订轮
（`max_revisions` 上限）→ 预算/步数护栏 → needs_human 升级到人。无自由规划。

**口径**：这是刻意设计，不是能力缺失。治理系统的第一要求是**可复核**——自由规划的
路径不可复核，所以把规划收敛为结构化循环，把不确定性关进修订轮预算里。引用评判标准
自身的话反守为攻："不要为了盲目追求多 Agent 架构而忽略业务本身"——本项目把这句话
执行到了治理层。失败恢复 = 修订轮 + 分类降级（infra_error 与 needs_human 分开），
最终结果验证 = 部署方预注册的确定性验证命令，不是模型自评。

### 标准四：上下文工程 —— 已知薄点，只准备答案

**事实**：交付线的上下文管理只有修订轮 feedback 传递与 goal 注入；支撑层
（`app/memory.py`、`context_budget.py`、`long_term_memory.py`、`knowledge_access.py`）
有会话记忆、上下文预算、长期记忆与知识库访问控制，但未形成交付线的展示面。

**口径**：先承认边界，再讲方法论——"上下文工程的本质是让模型在正确时间拿到正确信息；
在治理场景里，最关键的上下文是**验证结果与失败原因的结构化回流**（feedback 进修订轮），
而不是聊天历史堆叠。通用上下文管线在支撑层已有（记忆/预算/知识访问控制），交付线
刻意不引入——每多一层上下文就多一分不可复核性"。

### 标准五：可观测 —— 论点级强项

**事实**：trace_id / run_id 贯穿；GitHub / DeliveryRun / MergeRecord / 审计 WAL
四方证据对账；哈希链完整性报告（broken_at=None）；每次 LLM 调用记录
prompt/completion tokens 与时延。对应评判标准列的每一项（哪个 Agent、什么模型、
哪步失败、多快、多少钱、结果对不对）都有落点。

### 标准六：人机协同 —— 论点级强项，且有真实事件背书

**事实**：TTY 推送审批（非交互 stdin 自动拒绝）、合并审批带操作者身份与乐观锁、
高风险操作（推送 / 合并）全部人工节点。

**王牌事件——乱码事故**：一次交付因启动脚本编码缺陷（PS 5.1 把无 BOM UTF-8 按 GBK
解析）整体乱码入库，而当时的验证命令只断言 ASCII 哈希串、未能发现。这个事件同时
证明了三件事：① 验证命令的盲区会被真实流量暴露；② 修复走的是"人决策降级 + 全程
披露"，不是掩盖；③ 检测手段自此升级为全文 SHA-256 断言。**主动讲这个事故**——
面试官对"完美的 Agent"免疫，对"抓到自己盲区并改了测量方法"的候选人有记忆。

## 投递窗口内的打磨优先级（与定位清单一致）

1. dogfood 台账 ≥3 条真实交付（唯一依赖端点恢复的硬项；窗口内凑不满就如实记录降级结局）。
2. README 前屏关键词索引（本次已做，就绪标准 #2）。
3. 标准三 / 标准四：口头答案（本文），不开新工程。
4. 明确不做：补上下文工程代码、加多 Agent 协同、做演示网页——拿两周窗口换面试官
   不看的东西，且稀释"治理优先"的设计立场。
