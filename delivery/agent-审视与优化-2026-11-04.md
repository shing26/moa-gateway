# Agent 审视与重规划（2026-11-04）

> 视角：AI Agent 开发工程师（不是平台架构师）。
> 输入：`交付/` 计划、README、ADR-030/031/033，以及 `data/delivery-runs/` 里 8 条真实
> DeliveryRun 记录。结论先行，改动与重规划在后。

## 一、评判

### 1. 做得对的：治理底座是真的

- 状态机、审批门、bundle 哈希、head-SHA 乐观锁、审计 WAL 哈希链、四方对账，都有代码
  与真实记录支撑。`delivery run` 的失败分类（`needs_human` / `infra_error` /
  `budget_exhausted` / `verify_failed`）不是装饰，记录里确实各自出现过。
- 项目最难得的一点：**它愿意记录自己的失败**。台账第 2、3 行把"三次没做成"和"误挡"
  写得很清楚，这在作品集项目里比多一个功能更有说服力。

### 2. 真正的短板：产品路径上的 Agent 很薄

用 Agent 工程的标准看，交付 Implementer 只有四件事：四个工具、一个裸 ReAct 循环、
一条 goal、一次修订。问题不在"没有自由规划"（治理场景刻意收敛是对的），而在**任务
成功率所依赖的三件事没有做**：上下文经济、工具可发现性、失败证据回流。

真实记录给出的证据不是推测：

| 记录 | 结果 | 轨迹告诉我们的 |
|---|---|---|
| `dlv-0833c09f…` | `budget_exhausted` | 17 次调用、101 万 prompt token、39 步**全是 read/search、零 write** |
| `dlv-e74dc36b…` | `budget_exhausted` | 12 次调用、47 万 token、25 步同样零 write |
| `dlv-eefe0b5c…` | `failed / infra_error` | 预算 1.2M 被当成单次 completion 上限传给 provider，第一次调用即报 `Max tokens must not exceed 1048576` |
| `dlv-75263be0…` | `needs_human / verify_failed` | 验证环境缺 pytest；修订轮只收到"验证失败（exit=1）"，没有测试输出 |

这四条指向同一个结论：**产品当前的主要失败源不是门禁太严，而是 Agent 在预算内
完不成任务**。文档里"上下文工程是已知薄点、只备口头答案、不开新工程"的决定，在
dogfood 数据出来之后需要修正——这不是新模块，是产品主链路的缺陷。

### 3. 一个需要修正的叙事

README 的"受治理的仓库交付 Agent"是诚实的，但目前的证据重心仍偏向治理层。
面试官很容易追问："治理很好，那它到底能把活干成吗？" 台账第 1 行是人与 agent
协作、最终由人审批合并完成的；第 2、3 行没成。**下一阶段最该补的不是更多治理，
而是"真实任务完成率"的证据**。

## 二、本次做的优化（最小、可测、在主链路上）

原则：只改已经存在的交付循环，不新增运行时、不新增框架、不碰审批边界。

| 改动 | 文件 | 为什么 |
|---|---|---|
| 有界上下文策略提升到 `app/agents/`，交付与实验台共用 | `app/agents/memory.py`、`bench/agent/memory.py`（兼容 re-export） | 交付循环此前把全部历史反复送给模型，这是 101 万 token 的直接原因 |
| 工具循环每轮压缩：最近 6 轮全文，更早折成**一份**累计摘要 | `app/agents/stubs.py` | 压缩只作用于"发给模型的消息"；Run Record 的每一步观察仍然完整，可复核性不打折 |
| 观察按预算截断；`run_tests` 保留尾部 | `app/agents/memory.py`、`app/agents/stubs.py` | pytest 的失败摘要在尾部，只留头部会把最该看的裁掉 |
| 单次 completion 上限与总预算解耦（默认 8192） | `app/agents/stubs.py` | 修复已记录的 1.2M 预算直接打爆 provider 的错误 |
| 修订轮反馈带上命令、退出码、输出尾部 | `apps/code_review_pipeline/delivery/flow.py` | 原来只回一句"验证失败（exit=1）"，模型只能重猜 |
| Implementer 增加 `list_files`，提示词写清预算与"先定位再读、留额度给写入" | `.../adapters/production_agent.py` | 真实轨迹第一步就是 `read_file(".")` 失败，随后盲搜；它需要目录工具与预算感知 |
| 新增 `replace_in_file`：精确匹配替换；未命中/歧义判 `rejected` 并给出修正提示 | `app/agents/workspace_tools.py` | "零写入"的反面不是不想写，而是整文件重写的风险与 token 成本都高；小改动需要低风险落点 |
| 新增 `git_diff`：只读查看相对 baseline 的 status 与 patch | 同上 | 让 Agent 在收口前自检，而不是把"改了什么"留给审批人猜 |

验证：目标单测通过；新增用例锁住"压缩后早期观察不再原样进 prompt""审计步骤
仍保留全文""1.2M 预算只按 8192 请求 completion""修订反馈含退出码与输出"
"精确替换的歧义/未命中/CRLF 保留""git diff 的改动、未跟踪文件与无 baseline 降级"。

## 三、重规划（2026-11-04 → 2026-11-28）

### 原则

1. **停止扩治理层**。审批、审计、状态机已经足够讲 30 分钟；再加深边际收益很低。
2. **只做能提高真实交付完成率的改动**，每条改动必须能在 Run Record 里看到前后差异。
3. **每个主张都要有可点开的证据**；没有证据的能力不许进 README。

### 第 1 周（11/04–11/10）：把主链路跑成

- 用修好的循环重跑两个真实任务：
  1. `.github/dependabot.yml`（已完成过一次 `ready_for_push_approval`，补推送审批 →
     CI → 合并审批 → 台账；若实际未推送，就如实记为 smoke，不计入台账）。
  2. 飞书双向桥（issue #26）。先缩小 goal：只做 push 方向，或拆成两个交付；
     "多文件特性一次做完"正是第 2 行失败的原因。
- 验收标准：至少一条**全链路**真实交付（实现 → 验证 → 推送审批 → CI → 合并审批 →
  台账），并记录 token / 步数 / 是否用到修订轮。
- 不做：S1 Verifier、新渠道、自动修复 CI。

### 第 2 周（11/11–11/17）：给核心 Agent 补一个最小评测

现在有路由/守卫/RAG/审查的 eval，但**交付 Implementer 没有离线评测**，只有单测和
台账。这恰好是"Agent 工程师"最该补的一环。

- 复用 `bench/harness`（已有 fail-first、验证命令、防作弊还原），做一个 3–5 题的
  delivery 小集：单文件配置、双文件改动、需要读测试再改、一次验证失败后修订成功、
  预算边界内应停。
- 指标：pass@1、平均工具步数、平均 prompt token、修订轮成功率、`budget_exhausted`
  比例。每个任务固定 base SHA 与验证命令。
- 不新建框架；只做 `evals/` 下的一条 runner 与数据集。若时间不够，宁可只做 3 题，
  也不要用"演示成功"代替评测。

### 第 3 周（11/18–11/24）：投递就绪

- 干净环境 clone → 零网络演示 ≤5 分钟（就绪标准 #1，目前未打勾）。
- 台账 ≥3 条（#3），每条都有 run_id / PR / CI / 合并记录；凑不满就如实写降级结局。
- README 只改状态与证据链接，不再加功能章节。
- 简历每条主张 10 秒内能打开证据（#4）。

### 第 4 周（11/25–11/28）：冻结与演练

- 冻结代码；准备 10 分钟演示路径与 3 个追问的答案（并发、上下文、为什么不多 Agent）。
- 把本次"从真实失败记录定位到循环缺陷"的过程写进面试口径：这是比再做一个治理
  功能更强的信号。

### 明确不做

S1 只读 Verifier、自动 CI 修复/重跑、新 provider/渠道/dashboard、RAG 重开、
多 Agent 产品化、为演示改 prompt 骗守卫。理由不变：窗口内这些都不增加完成率，
只会稀释"治理 + 真实交付"的主线。

## 四、风险

| 风险 | 现状 | 处理 |
|---|---|---|
| 端点容量 | 免费端点曾 429 / 单次上限报错 | 每批前先跑 pilot；预算与 completion 上限已解耦 |
| Windows 验证环境 | 裸 `python`、临时目录、超时都出过问题 | 已修；每次交付记录实际验证命令与解释器 |
| 非 TTY 审批 | 非交互 stdin 自动拒绝 | 审批必须在真实终端完成，并在台账标注操作者 |
| 台账滞后 | 11/03 已有成功 run 未入账 | 只记录真实走完审批与合并的交付；dry-run 不计 |
| 过度宣称 | README 已较克制 | 所有"已修复"都以测试与 Run Record 为准 |

## 五、这次改动在面试里的讲法

> "我先看真实运行记录，不看架构图。8 条 DeliveryRun 里，失败主要不是门禁挡的，
> 是 Agent 在探索阶段把预算烧完了：17 次调用 101 万 prompt token，39 步零写入。
> 根因是交付循环没有上下文压缩，而实验台早就有了。我把策略提升到运行时共用层，
> 同时把'总预算'和'单次 completion 上限'分开——1.2M 预算被原样传给 provider
> 那次直接 0 token 失败。修订轮也改为回流验证命令、退出码和输出尾部。
> 可复核性没有牺牲：Run Record 保留完整步骤，压缩只作用于发给模型的消息。"

这段话同时覆盖：真实证据、根因分析、最小改动、可复核性边界、以及"不堆功能"的
判断力。
