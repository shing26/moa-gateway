> 用 Redis Streams + 独立 worker + 任务级幂等 + 审计链，把这件事做成
> 可演示、可复现的闭环。

   实测 `import app.main` 从 >150s 降到 2.6s，库不可达时 20s 内抛
   `StorageInitError` 而非静默丢数据。
   对照 `app/vectordb/pgvector_client.py`（早就有 `open_timeout_s`）——review_store
   是同源存储里唯一没有超时约束的一环。

## D2 交付记录（2026-10-01）

门禁：`pytest -q` **882 passed**（+13）｜`ruff check .` clean｜`git diff --check` 干净。

**判据状态：如实说明。** D2 原判据是"重复投递撞唯一约束 → 复用同一行"，这需要真
 Postgres。按约定本轮只做纯逻辑验证，所以该判据**尚未被证明**，留到 D3 起 Docker
 时一次性验。本轮实际证明的是：SQL 形状、迁移前提、以及三条**真库才炸**的适配错。

### 过程中改掉的两个设计

1. **`build_task_key` 不再把 sha 截断到 12 hex**（48 bit）。截断让 key 好看，但两个
   不同 commit 共享前 12 位就会得到同一个 key，而 `UNIQUE(repo, pr_number, head_sha)`
   **拦不住**——INSERT 会先在 trace_id 主键上冲突、走 `DO UPDATE` 覆盖前一条。
   即"加唯一约束"看着防住了重复，实际漏在更早的一环。同类分叉第四次
   （DSN 读取 / embedding 维度 / trace_id 的 `body['id']` / 这次的身份截断）。
2. **不新增 `task_state`，收编既有的 `status` 列。** 查过全仓库：`status` 只被写入
   （`save()` 写死 `'pending'`），**没有任何一处读它**——一列死数据。此时再加
   `task_state` 就是同一张表并存两套状态词汇，正是 `app/models/errors.py` 开头
   记下的教训。改为 `ALTER COLUMN status SET DEFAULT 'queued'` + 把遗留 `'pending'`
   归一，否则老行/新行会并存两套词汇。

### 三个真库才炸的错误（纯逻辑测试抓到的）

1. **jsonb 适配**：psycopg3 会把 Python 的 `list` 适配成 PG **数组**（oid 1005），
   而 `state_transitions` 是 jsonb 列。不显式包 `Jsonb` 的话，纯逻辑测试全绿、
   真库第一次写入就报类型不匹配。已加断言锁住包装类型。
2. **`DO UPDATE` 白名单**：只更新"这次投递能重新观察到的内容"（文件数、reviewers、
   是否需人工、updated_at）。`posted_review_id` 与 `status` **刻意不进白名单**——
   `EXCLUDED` 里它们恒为入队值（NULL / `'queued'`），无脑 DO UPDATE 会让每次重投
   把"已写回"抹成"未写回"（→ 重复评论）、把 done 拽回 queued（→ 违反"done 不重算"）。
   两种失效都**不报错**，只是安静地多做一遍 5 个 agent。
3. **冲突目标**：从 `ON CONFLICT (trace_id)` 改为 `ON CONFLICT (repo, pr_number,
   head_sha)`。trace_id 是"记录的地址"，三元组才是"这件事本身"，幂等属于后者。
   地址的派生规则变过（见上），挂在地址上的幂等会静默失效，而库里那条 UNIQUE
   还在、看着好好的。

### 去重步骤的真实理由

反直觉但重要：`UNIQUE(repo, pr_number, head_sha)` 在 trace_id 由三元组拼出的前提下
**是冗余的**（同三元组必同 trace_id，trace_id 是 PK）。去重防的不是老 bug 的重复行
——D1 之前所有 PR 挤成一行，三元组并不重复。去重防的是**本次自己造成的窗口**：
`build_task_key` 刚从"截断 12 hex"改成"完整 sha"，跨过这个窗口写下的行指向同一
三元组、trace_id 却各不相同。这正是保留 UNIQUE 的价值：让业务身份在库里显式存在，
不再只靠"trace_id 恰好同源"这个口头约定。

- `ReviewStore`（内存实现）**没有** `status` / `posted_review_id` 的概念。目前测试全走

### 挖出并修掉的三个真缺陷（都是纯逻辑测试测不到的）

1. **身份三列落库成空值**（最严重）。`save()` 从 `record.raw` 读
   `repo`/`pr_number`，而唯一的生产者 `github_review_route._record_from_result`
   传的是 `raw={}` → 那些 `.get(key, default)` 全部落默认值。真库里那行遗留数据
   就是物证（`repo=''`、`pr_number=0`、`trace_id` 却合法）。**D2 刚把幂等键定成
   `UNIQUE(repo, pr_number, head_sha)`，建在 ('', 0, sha) 上的唯一约束换个仓库的
   同一个 sha 就会误判成同一件事而合并。** 修：身份三列改从 dataclass 字段读，
   生产者补齐 `base_sha/title/html_url/diff_url`（NOT NULL 列写空串不报错，但留下
   空标题的空行）。真库回归：org-a/org-b 同 sha → 两条独立任务行。
2. **迁移无界等锁**。`schema.sql` 里的 `ALTER TABLE` 与非 CONCURRENTLY 的
   `CREATE UNIQUE INDEX` 都要 ACCESS EXCLUSIVE 锁；任何一条在途只读连接（哪怕
   没提交的 SELECT）就让迁移无限期排队。实测两个连续集成用例就能把 pytest 挂死
   >60s（pg_stat_activity 里 pid 一条 `idle in transaction`、一条 `wait_event=Lock`）。
   对 D3 尤其致命：worker 与 gateway 两个进程都在启动时跑迁移，会互相卡住。
   修：`options="-c lock_timeout=15000"` + `CODE_REVIEW_AUTO_MIGRATE` 开关
   （worker 不该在启动时改 schema）。
3. **lock_timeout 直传是无效的**（被自己的假单测漏掉）。`psycopg.connect(...,
   lock_timeout=...)` 在真库报 `invalid connection option`——它是 PG 服务端运行
   参数、不是 libpq 连接选项，必须走 `options`。假 psycopg 对任何 kwarg 都点头，
   所以"断言传了这个参数"的单测是绿的、行为是坏的。

### 值得单说的方法论教训

这轮最有价值的一条：**"纯逻辑测试全绿"曾连续骗了我两次**——
一次是 jsonb 传 Python list（psycopg3 适配成 PG 数组）、一次是 lock_timeout 直传。
两者在假连接下都完全正常，只有真 psycopg 会拒绝。判据"SQL 形状对"与"参数真的生效"
是两件事，前者可单测，后者只能真库证伪。所以新增
`tests/integration/test_task_idempotency_postgres.py`（8 条，compose 未起时 skip
不伪造通过），并注册 `postgres` / `redis` marker。

## 阶段二：步级副作用治理（约 3 天，严格排在阶段一之后）

### 前置：先得有"能改变世界的工具"

阶段二成立的前提是 agent 有手。当前 6 个工具全是只读或进程内便签
（`knowledge_search` / `current_time` / `calculator` / `list_documents` /
`add_note` / `get_notes`），没有一个能发 HTTP、写文件或改代码。
不先补这一步，"步级副作用分级"就是给空手套加锁。

新增每个工具前先问一句：它能让 agent 造成什么**外部**后果？

### 三级分类

| 级别 | 含义 | 守卫 | 审计 | 幂等键 |
|---|---|---|---|---|
| `read` | 读，不改变外部状态 | 免审 | 记 | 不需要 |
| `write_internal` | 改进程内状态（便签等） | 免审 | 记 | 不需要 |
| `external` | 有外部可见后果（发评论、推代码、调外部 API） | 必过守卫 | 记 | 必须有 |

### 三类拒绝，三种待遇

| 拒绝类型 | 喂给模型什么 | 轨迹 | 理由 |
|---|---|---|---|
| 参数被拒（schema 不过） | 完整错误 + 可修提示 | 继续 | 模型填错了，它自己能修 |
| 策略 DENY | 只说"该操作不被允许"，不给策略细节 | 终止 | 说清楚等于交出绕过地图 |
| 人工 REJECT | "人工拒绝" + 申诉入口 | 终止 | 再试是骚扰 |

绕过检测：同一 `(tool, target)` 在一条轨迹里被策略拒绝两次及以上，强制挂起
转人工。复用 FSM 已有的 `(RETRY, TASK_FAILED) → SUSPENDED` 结构，零新概念。

### 指标必须三分

`tool_errors`（环境挂了）、`tool_arg_rejections`（模型填错了）、
`tool_denials`（策略拦的）永远分开记。混在一起，eval 就测不出
"模型在乱试"与"环境在挂"的区别。

### 配套修正

- 步级审计行：`agent_name="agent_step"`，`extra` 记
  `action/tool/target/idempotency_key/step_index`。这正好填上"轨迹被算出来
  然后扔掉"的洞——当前 `TaskAgent` 内部的 `r.steps` 从不落库，进程退出即消失。
- `AGENT_MAX_STEPS` 从 3 提到 8~12，且从"配置项"降级为"审计指标"。
  真正的刹车是副作用分级，不是步数。

### 判据达成方式

`kill -9` 用 `_HardCrash(BaseException)` 模拟——连 `except Exception` 都接不住，
所以没有任何清理机会，与 SIGKILL 语义一致。崩溃点刻意选在**认领之后、落库之前**：
这是最容易丢任务的窗口。

### 过程中发现的设计缺口（真库集成测试逼出来的）

**「孤儿 running 任务」：worker 崩在认领后，任务永久卡死。** 首版实现只允许
`queued --claim--> running`，于是崩溃后重启的 worker 认领失败 → 跳过 → 任务永远
停在 running，**且不报任何错**。队列层看不出异常，PEL 也确实被清空了。

修法：新增 `RESUME` 动作（`running` 上的自环），且**只允许从 XAUTOCLAIM 路径发起**。
取舍写在这里以便日后复查：Redis 无法区分"原 worker 死了"与"原 worker 还活着只是慢"
——那一刻两者都是"空闲超过 min-idle-time"。本系统选择**当作它死了**（重跑一遍
5 个 agent）而不是当作它活着（任务永久卡住）。这是**至少一次执行 + 幂等副作用**
的必然结果，不是恰好一次。多 worker 场景还需要对在途消息做心跳（XCLAIM 自己）
以重置 idle 计时器；本轮"多 worker 水平扩"明确不在范围内，故未实现。

### 三个 redis-py 的真实坑（都是假连接测不出来的）

1. **XAUTOCLAIM 返回 `[next_id, messages, deleted]`**，游标在**第一个**元素。按
   "entries 在前"的直觉写会 unpack 出整数，报 `cannot unpack non-iterable int`。
2. **min_idle_ms=0 时它会永远返回同一条消息**，next_id 恒为 "0-0"。用
   "entries 非空就继续" 写循环 = **死循环**，worker 整轮就此卡住且无异常。
   终止条件必须是 next_id == "0-0"（本遍扫到流末尾）。
3. **游标与字段值都必须解码字节**。客户端 decode_responses=False，
   `str(b"0-0")` 得到 `"b'0-0'"`——它长得像合法 stream id，于是 Redis 报
   `Invalid stream ID`。同理只解键不解值的话 repo 会是 `b"org/app"`，查不到任务行，
   而表现是 worker 静默跳过、不报错。

另有一处 SQL 参数错误（6 placeholders but 3 parameters）也是假 cursor 放过的。

### 设计决策：队列消息只带身份，PR 数据现取

不把整份 webhook payload 存进任务行。两个理由：payload 很大（每个文件带 patch），
任务行会迅速膨胀；更重要的是它是**投递那一刻的快照**，等 worker 真正跑到时 PR
可能又推了新 commit，用快照审会审一个已经不存在的版本。build_pr_context_from_github
只需要 repository.full_name + pull_request.number，文件列表由 GitHub API 现取。

### 幂等双保险的分工（不是冗余）

主判据 `posted_review_id IS NULL` 覆盖绝大多数情况；marker 兜底补的是

## 再次修正：200671 是「回调地址不可达」，不是发送错误

上一节把 200671 归为"send_card 缺渠道判断"，**方向整个搞反了**。仓库里其实早有
记录——`scripts/start_stack.ps1` 的 DESCRIPTION 里写着：

> 2026-09-20 出过一次事故——容器停了 → 网关启动阻塞/退出 → 飞书卡片**回调**打到
> 隧道后 origin 无响应 → 客户端报 **200671「回调地址不可达」**。

也就是说 200671 出现在**入站回调**链路上：你点卡片上的批准/拒绝 → 飞书把回调 POST

200671。它与"卡片能不能发出去"无关。

这次为什么又找错了：前两轮都在 `send_card` 那条**发送**路径上找证据，而我从没
真的抓到过一个 200671 的现场。正确的顺序是先问"这条错误在哪个方向产生"，而不是
从最近改过的代码往回找。

`vectordb=PoolTimeout`（PG 连不上）。

这与 200671 无关，但会让 golden path 的任务状态**不持久**：worker 认领、
崩溃恢复、幂等那几条判据都需要真 Redis + 真 PG 才成立。

### 留下的教训

- 排查一个"只有错误码、没有堆栈"的外部错误时，第一步是**确认它发生在哪个方向**
  （入站还是出站），而不是从最近改过的文件往回找。
- 仓库里已有的事故记录要先读。`start_stack.ps1` 已经写着 200671 的成因与
  2026-09-20 那次事故，我跳过了它。
- 反复用 `Stop-Process` 杀进程做测试，结束时必须把服务恢复原状；否则下一个
  症状会被归因到刚做完的改动上。

## 依赖栈恢复实录（2026-10-03）

上面记的"网关没在运行"这次又复现了一次：进仓时 6380 / 5433 / 11434 / 8081
**四个端口全 DOWN**，容器也不在。跑一次 `scripts/start_stack.ps1` 即可全部恢复，
之后 `/healthz` 是 `redis=connected` / `vectordb=postgres`，不再是 degraded。

容器回来后重跑 golden path，**十九条判据全过且无一 skip**——此前依赖缺失时
worker 原子认领、kill -9 后 XAUTOCLAIM 接管、幂等双保险这几条是 skip 状态，
现在真跑了：投递 321ms、审计本轮 9 条、恢复后任务审计种类齐全。

### 一个只在 Windows PowerShell 下出现的坑

`demo/run_golden_path.ps1` 用 `powershell -File` 跑会直接 **ParserError**：
文件是 UTF-8 无 BOM，Windows PowerShell 5.1 按 ANSI 读，中文注释里的字节被
当成引号/括号，报出一堆"Unexpected token"。用 `pwsh`（PowerShell 7）跑正常。
要兼容 5.1 就得存成带 BOM 的 UTF-8；目前按"用 pwsh"处理。

### 系统代理会打断真 GitHub 通道（已修）

本机代理在 `127.0.0.1:31181` 上做 TLS 拦截，而它的根证书不在信任链里
（`SSL_CERT_FILE` 指向 anaconda 的 cacert.pem）。`httpx` 的 `trust_env` 默认为
True，于是 `GitHubClient` 的每次调用都死在 `CERTIFICATE_VERIFY_FAILED`。

这个故障**只出现在 GitHub 一侧**：飞书域名命中代理规则的 `*.cn` 直连例外，
两条路都通。所以症状看着像"token 无效"或"网络不通"，实则是代理。

修法：`GitHubClient` 默认 `trust_env=False`，需要代理的环境用
`CODE_REVIEW_GITHUB_TRUST_ENV=1` 打开。见 `a746b81`。

### 上一节的"Funnel 需要 cert.pem"是**错的**，已更正

我按"Funnel = Cloudflare Funnel"去查，于是只看到 `cloudflared` 缺 `cert.pem`，
就下了"connector 不在这台机器上"的结论。实际用的是 **Tailscale Funnel**，完全
是另一套东西：

- 它是 Tailscale 里的**常驻转发规则**，`tailscale funnel status` 就能看到，
  状态持久，Tailscale 登录着就会自动恢复——**根本不存在"启动 Funnel"这回事**；
- 不需要证书，connector 就在本机；
- 要改的只有一件事：指向哪个本地端口（`tailscale funnel --bg <端口>`）。

教训和 200671 那次同源：**别从一个专有名词直接推断是哪家的产品**。Funnel 这个
词 Cloudflare 和 Tailscale 都在用，先问清楚（或直接 `where tailscale` /
`tailscale funnel status` 试一次），比在错误的产品上排查快得多。

### 200671 的真正成因（本轮定案）

Funnel 一直指着 8082，而 8082 被另一个项目的容器抢走 → 那后面没有本网关在应答，
飞书回调拿不到响应 → 报 200671。所以这一次的链路是：

```
飞书 POST → 公网 https://laptop-todom8hg.tailcdb1fe.ts.net/feishu/event
         → Tailscale Funnel → 127.0.0.1:<Funnel 指的端口>
         → 不是本网关 / 没人听 → 200671「回调地址不可达」
```

已把 moa-gateway 移到 **8083**（`shoppilot-gateway-1` 占 8082），Funnel 改指 8083，
公网 `/healthz` 实测 200。端口选择的固化见下一节。

### 端口别再抢：`start_stack.ps1` 现在读 `.env`

此前 `-GatewayPort` 默认值**硬编码 8081**，且不读 `.env`——于是"改了 `.env` 的
端口却还得每次带参数"，漏带时就去和别人的容器抢。现在：

- `-GatewayPort` 省略（0）时依次读 `.env` 的 `GATEWAY_PORT`、`APP_PORT`，都没有
  再用 8081；显式传参仍然优先；
- 端口被占时**报出占用者是谁**（实测输出：`端口 8082 被 Docker 容器
  shoppilot-gateway-1（转发到 8082，宿主进程 com.docker.backend）占用`）。
  此前只说"被别的进程占用"，排查绕了三步才找到是哪个容器；
- 新增 `-GatewayHost`，默认仍是 `127.0.0.1`。同机 Funnel **不需要** `0.0.0.0`。

`.env` 里加了 `GATEWAY_PORT=8083`（该文件被 gitignore，所以只在本机生效）。

## 又一次假绿：golden path 验错了网关（2026-10-03）

把 `GATEWAY_PORT=8083` 写进 `.env` 之后，重跑 golden path——**十九条判据全过**。
但这次的全绿是假的。

`demo/run_golden_path.ps1` 自己起一个网关在 **8081**，而 `app.cli` 的 `--port`
默认值读 `settings.gateway_port`，也就是 `.env` 的 `GATEWAY_PORT` = **8083**。
于是投递全部打到常驻网关，本轮起的演示网关全程闲置。常驻网关有真 Redis + 真 PG
+ 同一条队列，worker 又是演示脚本自己起的，所以**每一条判据都对得上**：
202、耗时、幂等、审计 9 条、崩溃恢复，一条不差。

证据在访问日志里：常驻网关 `logs/gateway.out.log` 收到了 3 次
`POST /webhook/github/review`，演示网关 `demo/gateway.log` 收到 **0** 次。

修法与新增的自证判据：

- 端口可配（`GOLDEN_PATH_PORT`，默认 8081），且**启动前检查端口上有没有别人**——
  有就拒绝跑，不去抢；
- `review` 显式带 `--port` 指向本轮演示网关；
- 新增判据「**投递落在演示网关 (8081) 上，不是常驻网关**」：直接读演示网关自己的
  访问日志确那条 POST 出现过。这条判据就是为了让"验错实例"这种假绿再也过不去。

修完复跑：常驻网关 webhook 计数 6 → 6（一条没多），演示网关收到 3 条，
二十条判据全过。

### 修这个 bug 时踩到的两个 PowerShell 坑

1. **函数名 `Cli` 撞内置别名**：`cli` 是 `Clear-Item` 的别名。定义
   `function Cli(...)` 不报错，但调用时被解析到 `Clear-Item`，于是每次都报
   `Provider operation stopped because the provider does not support this
   operation`——报错与真正的原因（函数根本没被调用）毫无关系。改名 `Invoke-Demo`。
2. **`$rest[0] -eq "review"` 永远为假**：调用形如 `Invoke-Demo @("demo","review","42")`，
   `$rest[0]` 是 `demo`，子命令在 `$rest[1]`。条件写错导致 `--port` 静默不生效，
   而结果仍然是全绿——和上面那个假绿同源。
