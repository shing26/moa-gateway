## 5. 已排除项

- **不是网络**：同窗口 `integrate.api.nvidia.com` 的小 prompt 探针 4/4 成功
  （0.3–4.8s）；中等 prompt（约 3k tokens）3/3 成功（0.6–1.4s）。
- **不是 key 失效**：失败与成功在同一分钟内交替出现。
- **不是降级链污染**：`LLM_FALLBACK_MODELS` 已由 #178 钉空，日志中只有
  `model=nvidia/nemotron-3.5-super-vl-120b-a12b` 一个模型名。
- **不是并发**：runner 串行执行，一次只有一个用例。

**推断（非事实）**：在 6 RPM / 64k TPM 的负载下仍触发 429，更可能是该模型在
共享池中的容量被其它租户占满，或该 key 存在未公开的更严限额；单纯提高本 key 的
TPM 未必能解决。需要 NVIDIA 侧确认 429 是 key 级还是模型池级。

## 6. 对评测的影响（为什么必须解决）

`infra_error` 在预注册 §4 里是**排除项**，不进分子/分母。但这类失败不是随机缺失：
上下文越重的用例越容易在长对话中撞 429，被排除的恰恰是难例。按排除后的子集算
通过率会**系统性高估**模型能力。因此当前配额下不能产出可对外宣称的通过率。

## 7. 向 NVIDIA 提的关键问题

1. 该 key 对 `nvidia/nemotron-3.5-super-vl-120b-a12b` 的实际 RPM / TPM 限额是多少？
2. 上述 429 是 key 级限流，还是模型共享池饱和？请给出判定依据。
3. 能否提供专属 / scaled endpoint（可按量付费）？评测要求同一模型的可复现读数，
   共享池抖动会直接污染结果。
4. 若只能提限额，建议按**峰值 200k TPM、30 RPM** 配置，以覆盖单例 1.4M tokens
   的突发。
