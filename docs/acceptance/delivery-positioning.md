# 交付层定位与减法清单

日期：2026-11-05
状态：已接受（口径文档，非 ADR；与 ADR-030/031/033 同源，冲突时以 ADR 为准）
关联：ADR-029、ADR-030、ADR-031、ADR-033、`docs/acceptance/dogfood-ledger.md`

## 对外口径（一句话 + 三句边界）

**moa-gateway 是一个受治理的仓库交付 Agent：给定真实需求，它在一个隔离工作区里
实现、用该仓库的真实门禁验证，产出可复核的变更包；任何远端写都停在人工审批
之后，推送与合并是两道独立的人审闸口。**

边界三句：

1. 它保证的是**过程治理**（bundle 哈希、验证证据、审计链、两道人审），不是
   **结果正确性**——验证命令通过不等于改动值得合并，人审仍要看 diff。
2. 它的能力上限有测量：台账 6 行 17 次运行，单 Implementer、四工具、固定验证
   命令、不支持多轮交互。通过率与失败形状都在台账里，不另作修饰。
3. S1 只读 Verifier 是**预注册实验**（2026-11-05 预注册，门槛未满足、未开跑），
   不进入默认路径；在它通过门槛并出结论之前，对外不引用它。

## 减法清单（明确不做，每项带证据）

每一项都来自真实失败或真实成本，不是口味判断：

| 不做 | 为什么 | 证据 |
| --- | --- | --- |
| CI 自动修复 | CI 红只转人工（ADR-031 决策 7）。失败原因在依赖与权限的占比远高于代码本身；自动修会把"转人工"变成"瞎修" | 第 2 行三次 budget_exhausted；第 5 行 403 与 Postgres 停机 |
| 内容相似度阈值拦截改坏文档 | 实测改坏只占 3% 的行差，任何阈值都同时漏掉真损坏、误伤真重写。解法在工具层（覆盖上限 + 删除行报告），不在启发式 | 第 5 行 README 改坏（PR #44/#54） |
| 预算无限加档 | 两次 budget_exhausted 里有一次是工具缺陷伪装成预算不足；加预算是花钱掩盖诊断。先看轨迹归因，再动预算 | 第 6 行第 1/2 次运行：40→70 步，真因是 `-k` 引号切分（PR #51） |
| 多轮交互 / 追问澄清 | goal 一次性写清是治理要求；agent 不能在实现中途向人要上下文，否则两道人审闸口之间多出一条不受审计的通道 | ADR-031 决策 3；第 6 行 goal 全文前置的做法 |
| 队列 / dashboard / RAG / MCP / 多租户 / 新表 | ADR-031 决策 8。交付层的产品价值是治理链路本身，dashboard 不增加一条证据 | 台账全部 6 行都没有用到上述任何一项 |
| 为验收写一次性断言当验证命令 | 真实交付的定义（ADR-033 决策 1）：验证命令必须是仓库的真实门禁。第 3 行的误挡就是验证环境与真门禁脱节的产物 | 第 3 行 verify_failed（误挡）；第 4 行改用真实门禁后一次通过 |
| 静默降级模型 | 未配置强模型时以 `model_not_configured` 终止，不回落规则拼装（ADR-030 决策 8）。降级产出的 bundle 走的还是同一套人审，等于把治理成本花在已知的劣质输出上 | v6/v7/v8 的实验记录 |
| 追加新的能力开关 | 每个开关都要人审理解、台账记录、文档解释。S1 之前交付层只有一个拓扑开关，保持这个状态 | flow 层对 verified 拓扑显式拒绝，不静默 |

## 叙事里只讲测量过的事

- 可以讲：两道人审闸口 + WAL 审计 + fail-closed 验证；6 行台账（4 成）里每次
  失败的归因与对应修复；工具层缺陷→修复→下次交付通过的闭环（3 例）。
- 不讲："自主开发能力"、多 agent 协作的交付价值（拓扑 verified 未启用）、
  任何没有台账行支撑的可靠性数字。
- 台账里的失败**原样讲**：budget_exhausted 讲清是哪一层的原因（环境 / 工具 /
  能力），gate-blocked 与 escape 的区别不模糊（ADR-033）。
