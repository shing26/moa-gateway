# ADR-0021: PR 合并作为经审批的写操作

日期：2026-10-08
状态：已接受（待实施）
关联：ADR-013（HITL 回调信任）、ADR-019（审计链与保留）、
`apps/code_review_pipeline/routing/github_client.py`、
`apps/code_review_pipeline/routing/github_review_route.py`、`app/config.py`

## 背景

### 问题不是能力不够，是这些能力没有用户

本仓已经跑通的能力——原子认领、fail-closed 白名单、谁批的进审计、崩溃后不丢——
都是可靠性工程。但没有真实用户时，可靠性工程只能自娱。本轮追问的起点就是这句话：
项目"像个流水线产品，跟卖课项目差不多"，PR 审查 bot "没什么实际用处"。

审查 pipeline 的数据也印证了这点：8/5 到 10/1 之间**零条** code_review 记录，
10/2 之后全部是 golden path 演示（PR `#42`/`#43`，sha `demo0000…`）。
一个从未被真实 PR 触发的审查器，它的质量无从谈起。

### 现状证据：本仓既看不见 CI，也不能合并

`GitHubClient` 只有四个方法：

- `get_pr_files`（`github_client.py:52`）
- `get_pr`（`:60`）
- `list_reviews`（`:65`）
- `create_review`（`:86`）

**没有** check runs / workflow runs 的读取接口，所以 CI 结果读不到；**没有** merge 接口，
所以合并不了。`create_review` 的 docstring（`:97-98`）把立场写得很直白：

> 刻意不用 REQUEST_CHANGES——那是**替人做合并决策**，而这套系统的立场是给出可核查的
> 发现、由人决定要不要挡。越权动作不该由自动流程代劳。

入口侧同理：`github_review_route.py:60` 的 `REVIEWABLE_ACTIONS` 只有
`opened` / `synchronize` / `reopened` 三种，其余事件一律静默忽略（返回 200）。
该路由**不读 `X-GitHub-Event` 头**，所以推 `check_suite` 过来会被当成"不认识"丢掉。

结论：本仓当前是"能评论、不能行动；能看代码、不能看 CI"。这与第一个用户的真实需求
（看 CI + 合并）方向相反。

### 第一个用户的真实闭环

一周约 2 个 PR，流程是：

```
AI agent 写代码 → 提 PR → 跑 CI/测试
  ├─ 通过   → 用户手动合并（agent 没权限）
  └─ 不通过 → 用户看日志 → 手动转述给 agent → 修 → 再跑 → 用户手动合并
合并之后 → 文档不更新
```

三个候选痛点里，前两个（等 CI、手动合并）每天发生；第三个（文档漂移）用户描述它时的
语气是"我知道应该做但没做"，不带情绪——它是愧疚感，不是痛点。

### 关键观察：手动合并的原因是权限，不是 branch protection

用户原话："**除了一些没有权限的 Agent 需要我自己上 GitHub 进行手动合并**"。

这说明差别在**权限**，不在能力：有权限的 agent 能自动合并，没权限的要人代劳。
于是本 ADR 的核心推论是——**只要网关持有合并权限，agent 就不再需要自己有权限，
它只需要能让网关听见。**

## 决策

### 1. 定位：从"只读评论"进化为"经审批的写操作"

补齐两个原语：**读 CI 状态**与**合并 PR**。动作本身由网关执行，但**必须过审批门、
必须进审计链**。原先"越权动作不该由自动流程代劳"的立场**不推翻**，而是被修正为：
不是"绝不替人做"，而是"**人批了才做，且全程留痕**"。

审批门不是给动作加障碍，它正是"有副作用的动作"与"自动流程"能够共存的唯一方式。

### 2. 权限收拢：合并权限从 N 个 agent 收拢到 1 个网关

这是本项目最硬的一处差异化。对比：

| | 现状（每个 agent 各自持有 token） | 本 ADR（网关持有，agent 只请求） |
|---|---|---|
| 权限面 | N 个 token，各自过期/泄漏 | 1 处，可审计 |
| 无权限的 agent | 只能人代劳 | 能请求，人只审批 |
| 审计 | 分散在各 agent，无法归集 | 单一审计链 |
| 复用 | 每个 agent 各写一套 | 任何 agent 共用一条通道 |

### 3. 入口：推模型，第一版只做这一条

```
CI 结果 → 网关判断 → CI 绿 → 飞书弹审批卡片 → 用户点批准 → 网关合并 → 审计
                    → CI 红 → 推失败 job 名 + 日志链接
```

拉模型（别的 agent 主动调 API 请求动作）**不在第一版**。理由：成功标准是"自己真在用"，
推模型不需要改任何 agent 就能上线，是唯一能立刻验证的形态。拉模型是第二步的通用化。

两者不冲突：核心是"动作请求 + 审批门 + 审计"这一条通道，推与拉只是两个入口。

### 4. 边界：CI 绿弹卡片，CI 红推失败信息

CI 红时**只做信息整理**——把失败的 job 名字与日志链接推给用户，由用户决定要不要转给
agent 修。**不做自动修复**。理由：自动修复是一个 LLM 修复环，有自身的不确定性，
会把项目重新拉回"落点太多"。它消灭的是"转述"这个动作，而不是"修"。

### 5. 与现有审查 pipeline 的关系：降级为卡片上的参考信息

CI 绿即弹卡片；卡片上**顺带**列出"审查发现 N 个问题，点这里看"。审查**不是**硬门禁。

明确否决"审查作为合并前置门禁"：用户自己都判断审查"没什么实际用处"，让一个未经验证
的审查去挡合并，等于让不信任的东西替人做决定。

这条决定同时给审查 pipeline 一次公平审判：它不再自成一摊，而是必须在真实合并决策里
反复出现。用户总是点开看 → 它活下来；从来不看 → 它确实该砍。**让使用数据回答，
而不是现在拍脑袋。**

### 6. 成功标准（唯一）

**连续 10 个 PR（按一周 2 个，约 5 周），合并动作全部走本通道，用户一次都没打开过
GitHub 的合并按钮。**

它有明确的失败判据：中途若发现自己还是习惯性去 GitHub 点合并，就是没成功，不许糊弄。
这正是本项目缺的那个"不假绿"的标准。

"别人也能用"与"面试讲得清"都不作为目标：前者太远，后者是副产品。**A 达成了，副产品
自然有**；把面试当目标，就会又做出一个演示品。

### 7. 明确不做（第一版）

1. **不做拉模型**——别的 agent 主动调 API 是第二步。
2. **不做 CI 自动修复**——决策 4 的推论。
3. **不做文档自动更新**——最多在合并成功的通知里带一句"这个 PR 动了 `docs/` 下 N 个
   文件"。不生成文档、不建 PR。理由见背景里"愧疚感不是痛点"。
4. **不做多用户 / 多租户 / 权限系统**——成功标准决定了只有一个用户。
5. **不做飞书以外的渠道**——Slack / 钉钉 / 邮件一律不做。
6. **不改审查 pipeline 的算法**——它现在什么样就什么样，只改变它在流程里的位置。
7. **不做生产级持久化**——checkpointer 保持现状，不升级 Redis / Postgres。
8. **不替换 FSM**——LangGraph 那条线（ADR-008）不碰。

## 实现落点（工程判断，不占用用户决策）

以下为实现细节，记录在此以便评审，不属于需要用户拍板的产品决策。

### CI 结果的采集：复用已有 PR 记录 + 轮询

- **PR 身份已有**：现有 `pull_request` webhook 在 `opened` / `synchronize` / `reopened`
  时已经收到事件并落库（`record_from_webhook`）。"该盯哪些 PR"这件事不需要新写。
- **CI 状态用轮询，不用 check 事件分派**。理由：
  1. 网关跑在笔记本上，经 Tailscale Funnel 暴露。笔记本休眠时 GitHub 推来的事件会丢，
     轮询在恢复后能补上；
  2. GitHub 的 CI 结论分散在 `check_suite` / `check_run` / `workflow_run` / `status`
     四种事件里，语义各异；而 REST 侧只要聚合
     `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` 与 `/status` 就能得出
     "是否全绿"，复杂度低得多。
- **不依赖 `X-GitHub-Event`**：现有路由不读该头，本 ADR 不要求改动它；CI 判断走独立路径。

### 合并：用仓库默认方式，合并前校验可合并性

- 不写死 `merge` / `squash` / `rebase`，用仓库自身配置的默认合并方式，避免替用户做风格决策。
- 调用 merge 前先读 PR 的 `mergeable` / `mergeable_state`。冲突（`dirty`）时**不尝试合并**，
  直接按失败路径通知，不自动 rebase。

### 审批与审计：复用现有资产，不新建

- 审批人白名单与开关复用现有 HITL（`app/config.py:110-114`，`hitl_approver_ids` 非空即强制）。
- 卡片走现有飞书通道。
- 每次动作写现有审计链（ADR-019）。"谁批的、批了什么、什么时候"必须落在链上，
  这是本 ADR 相对"给 agent 发 token"的唯一不可替代之处。

### 幂等：沿用 `task_key` 模式

同一 PR 的同一 `head_sha` 只允许产生一张待批卡片。CI 重跑、webhook 重投、卡片重复点击
都不得重复合并。身份沿用 `build_task_key` 的思路（`repo#pr@sha`），但**必须使用完整 sha**——
该函数注释里已经记录过"截断到 12 hex 是假安全"的教训。

### 失败路径：如实通知，不自动重试

合并失败（冲突、branch protection 拒绝、token 权限不足）时，把 GitHub 返回的原因原样
推给用户，**不自动重试、不自动降级成别的合并方式**。

## 验收

### 产品验收（唯一硬指标）

连续 10 个 PR 的合并动作全部经本通道完成，期间用户未打开过 GitHub 的合并按钮。

### 技术验收

1. CI 未绿时**不产生**待批卡片；CI 由红转绿后产生。
2. CI 红时推送失败 job 名与日志链接，且**不**触发任何自动修复动作。
3. 批准后合并成功；合并动作在审计链上留下"谁批的、批了什么、何时"。
4. 同一 `head_sha` 重复投递/重复点击不产生第二次合并。
5. 合并失败时用户收到真实原因，且系统状态可恢复（不卡死、不静默）。
6. 现有审查 pipeline 的行为**零回归**（它只是多了一个被引用的位置）。

### 诚实标注

- 本 ADR 只确立方向与边界，**尚未实施**，因此没有任何实现层面的证据。
- "CI 红时推送的失败信息对用户是否真的有用"属于未验证假设：若用户从不点开链接，
  决策 4 的一半（红侧）也应重新评估。

## 后果

- **审查 pipeline 的位置变了**：它从"独立产物"变成"合并卡片上的一段参考信息"。
  它的存废从此由使用数据决定，而不是由它自身的复杂度决定。
- **`README` 存在一处需要同步的漂移**：README 第 308 行附近称"PR 审查是只读审查，
  `GitHubClient` 只有 `get_pr` / `get_pr_files`，没有写回"，但代码里早已有
  `create_review` / `list_reviews`。本 ADR 落地时会进一步引入 merge，该表述必须一并修正。
- **权限集中的风险**：合并权限收拢到网关后，网关的 GitHub token 成为单点高价值目标。
  这是"权限收拢"的代价，第一版接受它，但必须在部署侧明确该 token 的存放与最小范围。
- **审计链的完整性变得可验证**：从"演示数据"变成"每周 2 条真实记录"，这是本项目
  第一次能让审计链面对真实流量。
- **不得顺势扩大宣称**：在连续 10 个 PR 达成之前，README 与简历只应写"支持经审批的
  PR 合并通道"，**不得**写"自动化 PR 合并"或"CI 自动修复"。
