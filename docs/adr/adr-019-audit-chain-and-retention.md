# ADR-0019: 审计链的 tamper-evident 边界与容量口径

日期：2026-09-28
状态：已实施（2026-09-28）
关联：ADR-004（Audit Logging，本 ADR **修正其"不可篡改"的声称**）、ADR-016（台账，本项属表外新发现立项）

## 背景

审计 v2 判定 moa-gateway 的"不可篡改审计"不成立；复核逐条确认，且发现口径问题不止一处。
代码集中在 `app/audit/wal.py`。

1. **明文 append，无链。** `_write_disk`（`:107-119`）是 `json.dumps(record)` + `open(path, "a")`
   追加。任何有磁盘权限者可原地改一条而不留痕——**append-only ≠ 不可篡改**。
2. **容量口径与落盘不一致。** `estimated_bytes`（`:101-104`）求 `sum(len(e.agent_output))`，
   但落盘前 `record.pop("agent_output", None)`（`:113`）把该字段丢掉了；而且 `len(str)`
   是**字符数不是字节数**（中文与 emoji 差 3~4 倍）。于是这个"容量"既不等于写入量、也不是字节。
3. **满载静默丢最旧。** buffer 是 `deque(maxlen=100_000)`，满时最旧条目被静默挤掉，无计数、
   无告警、无落盘兜底。
4. **`replay_all` 无业务消费者。** 全仓没有调用它的业务方（只有测试）。也就是说这个 buffer
   实际上是"最近窗口"，**不是**完整审计源——这一点此前没有写明，容易被当成完整审计链读。

## 决策

1. **做 tamper-evident（防篡改可发现），不做 tamper-proof。** 每条审计写入
   `prev_hash` / `entry_hash`（对前一条哈希 + 本条规范序列化做摘要）。全仓库与对外材料
   统一改口径为 **tamper-evident**——链式哈希能证明"第 N 条之后被动过"，**不能**阻止
   有磁盘权限的人整条重写。继续写"不可篡改"是把声明说过头（ADR-015 正打这个）。
2. **链头写失败不得中断审计。** 链头（前一条哈希）读取/写入失败时，降级为
   "**进程内续链 + 告警**"，而不是让审计因一次 IO 抖动整体中断。审计漏一条哈希，
   比审计整条链路死掉更可接受——但降级必须**可见**（计数/日志），不得静默。
3. **容量口径改为与落盘一致。** `estimated_bytes` 改为按**实际写入行的字节数**统计
   （或改名以如实命名，如"写入量"）；不再用 `len(agent_output)` 这个落盘并不包含的字段。
4. **满载不得静默丢。** 给溢出定明确策略并暴露计数（如 `wal_dropped`）：落盘兜底 /
   背压 / 至少告警三者选一，**不能什么都不做**。
5. **文档写明 buffer 的真实性质。** `replay_all` 当前无业务消费者，buffer 是最近窗口而非
   完整审计源；避免后续读者据它推断"审计完整可回放"。

## 验收

1. 篡改任意一条历史记录后，校验能定位到该条（返回第一个断裂点），未篡改时校验通过。
2. `estimated_bytes`（或改名后的同类指标）与实际写入文件字节数一致（中文用例下也成立）。
3. 满载行为有测试：溢出时既有可观测信号（计数/告警），且**不静默丢**。
4. 链头 IO 失败注入测试：审计继续写入、降级信号可见、不抛断链路。
5. 零回归。~~ADR-004 的"不可篡改"表述同步修正为 tamper-evident~~（见下文实施记录：
   ADR-004 里**并没有**这个声称，"修正"是多余的）。

## 实施记录（2026-09-28）

决策 1–5 已落地：`app/audit/models.py`、`app/audit/wal.py`、`tests/unit/test_audit_chain.py`、
`README.md`。两处需要记下来：

- **决策 5 的前提有一处不成立：ADR-004 里并没有"不可篡改"的声称。** ADR-004（Audit
  Logging）通篇只讲 PIPL 合规需要审计轨迹与落盘/检索设施，没有写 tamper-proof。所以
  "同步修正 ADR-004"是**多余的**——本 ADR 保留这条、只注明它不成立，免得下次有人照着
  去改一个不存在的声称。真正需要对齐的对外措辞在 README，已在那里写明 **tamper-evident**
  并显式标注"不是 tamper-proof"。
- **`delivery/系统设计.md` 有一行"不可篡改保障｜独立账号/独立桶；与业务存储物理隔离"**：
  那是一张**合规需求表**的取值（"要求是什么"），不是"本仓已实现"的声称，因此**不改**
  ——把需求本身改弱才是失真。

落地细节（几处不在决策里、但影响正确性的选择）：

- 哈希覆盖**实际写下的字段**（`to_audit_dict()` 去掉 agent_output 全文）。若让哈希覆盖
  被 pop 掉的字段，从日志文件本身就不再能重算校验——链只在内存里成立，落了盘就验不了。
- 链字段加在 `AuditEntry` 上、而不是只加在 WAL 里：两个 sink 共用 `to_audit_dict()`，
  字段集合不变量（`test_audit_field_coverage.py`）因此自动成立；ES 读的是 WAL 写过的
  同一个对象，两个 sink 的哈希一致。
- **每个日文件是一条独立的链**（首行 `prev_hash` 为空），进程内重启从当日文件尾恢复链头，
  所以同一天内连续；跨日不接续是刻意边界，已写进 `verify_chain` 的 docstring。
- 续链失败（文件损坏 / 读不动）**不掩盖**：以空 `prev_hash` 起新链，`verify_chain` 会
  如实报断裂——"无法证明连续"应当可见，而不是悄悄补一个看似连续的链头。
- `estimated_bytes` **改名**为 `buffered_bytes`：口径变了名字就得跟着变，否则下一个人
  会按旧语义用它（旧口径是 `len(agent_output)`，既不是写入量也不是字节）。

## 补记：链从"每文件一条"改成"每写者一条"（2026-09-29）

**触发**：启动服务做验收时，`/healthz` 报 `审计链断裂 audit-2026-09-29.jsonl:25`。
查下来第 24/25 行分别是 `qa-p3-5` 与 `qa-p3-6`——**QA 探针的两个会话**，即同一天有两个
进程写同一份 `audit-2026-09-29.jsonl`。

**根因（本 ADR 决策 1 的一个未言明前提被证伪）**：`_resume_chain` 从**文件的最后一行**
恢复链头，而链被隐含地当成"整份文件一条"。多进程写同一文件时，两个进程都从同一个
（别的写者的）链头往下接，交错写入 → 后写入那行的 `prev_hash` 对不上前一行的
`entry_hash` → 校验报"被改过"。**那是假阳性，而且是最坏的一种**：tamper-evident 一旦
对正常运维行为报警，它就会被忽略，等于没有。

**改法**：每行写入 `writer`（`hostname:pid`，进哈希覆盖范围），链改成**每写者一条**：

- `chain_report` 按 `writer` 分组，各自维护链头 → 交错互不干扰；
- `_resume_chain` 在文件尾窗口里找**本写者**的最后一条（不是文件最后一条）；
- **宽容交错不等于放过篡改**：删掉某写者的一行 → 它下一行的 `prev_hash` 对不上；
  删掉 `writer` 字段 → 该行自成一组、首行 `prev_hash` 非空 → 照样断裂。两条都有用例钉住。

**残留（如实记）**：本改动之前写下的行**没有** `writer` 字段，全部归入同一组，因此那份
文件仍会（正确地）报断裂——它们无法按写者归因，"无法证明连续"就该说出来。第二天文件
滚动后即干净。另：`_resume_chain` 只在文件尾 64KB 窗口内找本写者；若本写者上次写入落在
窗口之外，恢复不到 → 以空链头起链 → 校验如实报出那一处断裂（不假装连续）。

## 后果

- 审计语义从"append-only 即不可篡改"修正为"**链式可发现篡改**"。这是一次**降低声称**
  而非提升能力——但它是真的，而原来的声称是假的（ADR-015 精神）。
- `AuditEntry.to_audit_dict()` 作为字段单一来源（`:113` 已在使用）继续保留；本 ADR 只在
  其上增加哈希字段与口径修正，不重开白名单。
- 链式哈希会给写入路径增加一次前序哈希读取；按决策 2，该读取失败不得成为写入失败的
  理由。这与"审计可用性优先于链完整性"的取舍是刻意的，需在实施时写进代码注释。
