# ADR-027: 并行专家使用独立写集并在分歧时保留原文件

## 背景

协作图用 `Send` 在同一 superstep 并发执行多个专家。此前所有专家拿到同一个
`workspace_path`，`write_file` 直接落共享工作区；两个专家写同一路径时结果取决于
调度和完成顺序。这个行为无法从 Run Record 复原，也无法判断最终内容是哪个专家写的。

直接加文件锁只能避免同时写，不能回答“两个候选都应该如何处理”。静默串行化仍会让
后一个写入覆盖前一个，只是把竞争变成了不可见的顺序依赖。

## 决策

1. 每个专家执行前从共享工作区创建独立副本；专家工具和验证命令只看到这个副本。
2. 专家结束后比较源工作区与副本，生成文件级写集，记录写入者、路径、变更类型以及
   前后内容哈希。
3. 并发层只通过带 reducer 的 `workspace_write_sets` 回传写集；执行专家本身不修改
   共享工作区。
4. 下一派发节点按路径合并写集。不同路径全部保留；相同路径且相同 after hash 的写入
   只落一次；相同路径且 after hash 分歧时不选择赢家，保留原文件。
5. 写集所基于的 before hash 与当前文件不一致时同样记 stale-base 冲突，不尝试三方
   合并或强制覆盖。
6. 冲突作为 `workspace_conflicts` 进入 Run Record；合并结果作为 `workspace_merges`
   落盘。失败的专家写集保留为 `accepted=false` 证据，但不参与合并。

## 替代方案

- **共享工作区加锁**：可避免同时写，但仍是后写覆盖；无法保留两个候选。
- **只允许一个专家写文件**：会退化并行分工，也无法覆盖两个专家都需要修改同一模块的
  真实任务。
- **自动三方合并**：在缺少语义冲突判断时会把“能拼起来”误当作“逻辑正确”。
- **冲突时选择字典序最小写入者**：结果确定，但仍然静默丢弃另一个候选，不符合
  可复核要求。

## 后果

- 并行 Worker 需要支付一次工作区复制成本；当前优先保证正确性与证据完整性。
- 冲突会让该路径保持不变，需要后续 Critic、人工或显式修订轮处理。
- 写集正文只存在于运行中的图和隔离副本；Run Record 保存摘要与哈希，不保存所有文件
  正文。完整候选可通过受控复跑重建。
