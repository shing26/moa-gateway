# E3 合成缺陷任务规格（票 10）

真实历史 bug（E1）的数量与难度分布是**给定的**：能挑出多少条取决于 git 历史里
恰好有多少"修复 + 测试"同 commit 的收敛改动，改大改小、难易比例都不是我们能动的。
E3 把难度变成**可控变量**：同一个功能面上，训练者按需要造出"改 1 行"到"改 60 行"
的任务，剂量曲线的横轴因此可以按设计铺开，而不是被历史偶然性牵着走。

代价是合成缺陷天然带一个 E1 没有的风险：**出题人知道答案**。所以这份规格的重点不是
"怎么造 bug"，而是**什么样的合成缺陷算合格**——尤其是它不能比 E1 更容易被猜中。

## 1. 任务形态

E3 任务与 E1 任务**共用同一个落盘格式**（`bench/tasks/<id>.task.json` +
`<id>.test.patch` + `<id>.solution.patch`），因为 harness、fail-first、还原、
报告全都已经围着这个格式建好了；E3 不是一个新机制，是同一机制的第二类原料。

两者的差别是来源语义，不是格式：

| | base_commit | test.patch | solution.patch | `source` |
|---|---|---|---|---|
| **E1** | 修复 commit 的父提交（真实历史） | 该 commit 里 `tests/` 的那半 | 该 commit 里非 `tests/` 的那半 | `"E1"` |
| **E3** | 一个干净的历史提交（题面基线） | **注入缺陷**到真实源文件 + 新增行为判据 | 只含修复（缺陷的反向） | `"E3"` |

E1 的缺陷来自历史，E3 的缺陷来自 `test.patch` 里的注入——agent 看到的坏代码与
E1 完全同构，但它是我们按难度设计出来的。`source` 字段把两类分开，报告里可按来源
切片（同一条剂量曲线里混着 E1/E3 时，"E3 是不是更容易"这种问题才有分母）。

## 2. 合格判据（硬性）

一条候选要落成 E3 任务，必须**全部**满足；任何一条不过，连同原因一起记进剔除清单
（见 §5），不"先收下以后再说"。

### 2.1 fail-first 必须失败，且失败落在修复面上

与 E1 同一条守卫（`bench/harness/runner.py::run_task`）：物化
"base_commit + test.patch" 后，`verify_command` 必须**非零退出**，否则任务被判无效
并剔除——不失败说明缺陷没注入到判据能看见的地方，后面所有数字都是假的。

退出码非零还不够：**导入错误、收集错误也非零**。所以每条 E3 任务在守卫里钉住自己
的失败特征（`EXTRA_FAIL_FIRST_MARKERS` 同款写法），失败摘要必须命中，挡住"import
挂了也算 fail-first"这条假阳性。

### 2.2 修复必须使判据收敛

`solution.patch` 应用后，`verify_command` 必须**零退出**，且只改非测试文件——
否则这不是"修复"，是"把判据绕过去"。端到端用 scripted agent 写回 solution 那半，
判决必须 `pass`。

### 2.3 只改测试必须判 fail

与 E1 同一条：agent 只改测试文件 → 还原整棵测试树后判据仍在 → 判 `fail`。
E3 的判据是拿"注入的缺陷"当红的，这条守卫证明红不是测试自己制造出来的。

### 2.4 判据是行为级，且**不可一眼看穿**

这是 E3 最容易被做废的一条，所以拆成两个可核查的子条件：

**(a) 行为级**：判据断言**公开入口的可观察行为**（返回值 / 排序 / 状态码 / 落盘
字段），不引用私有符号、不断言实现细节、不 `mock` 内部协作者。测试在重构后仍应
成立——"改代码就红、行为没变也红"的测试不是判据。

**(b) 不可一眼看穿**：**判据文本不得直接说出缺陷的位置或修法**。具体禁止：

- 用例名 / 模块注释里点名被测私有函数（`test_foo_returns_bar` 式的实现级命名）；
- 断言里硬编码缺陷那一行该改成什么（"期望 `min(..., 1.0)`"这类）；
- 用例本身构成"把修复抄一遍"——即把 solution 的逻辑在断言里重算。

允许的是：断言一个**业务可见的后果**（排序变了、限流没触发、响应被拒），让 agent
不得不读源文件、把行为反推到缺陷所在。判据可以长、可以覆盖多个行为，但不能是
"缺陷位置的指针"。

### 2.5 现有测试不因注入而变红

注入缺陷后，除了本任务钉住的那条新判据，仓库既有测试必须仍然全绿。否则 agent 只要
在测试树里搜"今天变红的那条"就能直接读到答案，等于把 §2.4 作废。

这条是**筛选项**，不是运行期守卫：跑一次"注入后全量 `pytest tests/unit`"，
记录红的是不是只有新判据。若有既有测试变红，候选剔除或改用不触及既有断言的缺陷。

### 2.6 patch 可应用且是 LF

`test.patch` 与 `solution.patch` 都必须能 `git apply --check` 到 `base_commit`
物化出来的树；两个 patch 都必须是 **LF**（`.gitattributes` 已把
`bench/tasks/*.patch` 钉成 `text eol=lf`，新增文件不能破这条——`core.autocrlf=true`
的克隆上 CRLF 上下文会直接 "patch does not apply"，实测过）。

## 3. 难度声明（`fix_surface`）

E3 的价值在于难度**可调**，所以每条任务在 `task.json` 里带一个显式的
`fix_surface`（单位：solution.patch 的有效改动行数），报告与剔除清单都按它排序：

| `fix_surface` | 含义 | 本轮 |
|---|---|---|
| `small` | 1–2 行，单点逻辑 | 2 条 |
| `medium` | 3–8 行，一个函数的几处分支 | 1 条 |
| `large` | 9+ 行，跨分支 / 跨函数的收敛改动 | 0 条（首批未凑出，见 §5 剔除清单） |

`fix_surface` 是**声明**，不是实测；实测的"这个面到底多大"由 solution.patch 行数
说话（§5 的落地记录里逐条写实数）。声明与实数不一致时以实数为准并回填声明——
难度是可控变量，谎报它等于把这条 ticket 的初衷做没。

阈值按首批实测回填过一次（初稿写的是 1–5 / 6–20 / 21+，与实测的 1 / 4 / 2 行
对不上；`large` 一档首批没有合格候选，如实留空，不为了填满表硬造一条）。

## 4. 报告口径：按来源区分

§5.4 的剂量曲线表已有 `task_id` / `arm` / `outcome` 三个维度。E3 落进来后还需要
第四个维度：**来源**（E1 / E3）。缺了它，报告只能说"这张表"，不能说"E1 与 E3
各自表现如何"——而那正是"合成缺陷是不是把难度做成了可控变量"的唯一证据。

落地：`TaskSpec.source` → `RunResult.source` → 落盘 JSON → `RunRow.source`，
报告层按它展示每格的来源集合。默认 `"E1"`（既有 5 条任务 `task.json` 里本来就写了
`"source": "E1"`，不动的任务不用回填）。

## 5. 首批与剔除清单

首批候选、各自的 `fix_surface`、fail-first 实测特征、以及被剔除候选的原因，
记录在 `.scratch/bench-agent/issues/10-e3-synthetic-defects.md` 的「落地」段
（那是指向本规格的、带日期与实测输出的运行时记录）。规格这边只定"什么算合格"，
不复制易过期的实测数据。

## 6. 本 ticket 的边界

- **不跑真实 API**：E3 只做到"任务落盘 + fail-first 筛过 + 报告可区分"，
  真实曲线仍是 09 的事。
- **不阻塞 09**：09 的第一轮曲线可以只用 E1；E3 是加料，不是前置。
- **不动 `app/` 的行为**：E3 的注入只活在 `bench/tasks/` 的 patch 里，不进仓库
  源文件、不进 CI。
