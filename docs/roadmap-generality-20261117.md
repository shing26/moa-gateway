# 路线图：从「我机器上能跑」到「第二个人在自己的仓库上能跑」

**日期**：2026-11-17　**定位**：私有化部署的治理交付代理，不做 hosted。
**第一要点**：通用性。功能深度让位于「别人能用」。

---

## 0. 判据：什么叫「可交付」

一句话验收：**第二个人，拿他自己的 GitHub 仓库和他的 PAT，在他自己的机器上，
不改 moa-gateway 一行代码，能走完整条链路。**

链路 = 仓库档案 → DeliveryRun → 验证 → 打包 → 人工推送审批 → PR → CI →
人工合并审批 → MergeRecord → 审计对账。

这条判据同时否掉了三种「自嗨式交付」：

| 假交付 | 为什么不算 |
|---|---|
| 「我能跑通」 | 你的机器、你的 PAT、你的 TTY，都是不可复制的环境 |
| 「有文档」 | 文档没被第二个人执行并记录踩坑，等于假设 |
| 「通过率 48%」 | 单点读数，不是分布；对外宣称需要 n≥3 轮 + 区间 |

## 1. 六层拆解（按阻塞程度）

### A. 审批渠道层 —— 唯一硬阻塞

| | 现状事实 | 缺口 |
|---|---|---|
| A1 远程审批 | `app/routes/feishu.py`、`app/routes/webhook.py` 已有审批路由与 `HITL_APPROVER_IDS` 白名单（`app/config.py:114`、`app/middleware/auth.py:36`） | 回调地址 `https://laptop-todom8hg.tailcdb1fe.ts.net` → `127.0.0.1:8083`，**8083 无监听**；仓库无 GitHub webhook；`.env` 无 `DELIVERY_WEBHOOK_ENABLED`。与 nexus-vibe 的地址共用是搁置原因，需确认是否解除 |
| A2 多操作者身份 | 终端审批（`app/cli.py:340`）**只读一个自由输入的 `approver` 名字**，不校验白名单、不校验是否等于推送者；白名单只在 Feishu/webhook 路由生效 | 审批人身份与操作者身份未分离；终端路径可自我审批（同一人 push 同一人 APPROVE）；HITL 白名单在两条通道上语义不一致 |

**关键判断：A2 真于 A1。** A1 是「在哪个渠道审批」，A2 是「审批能不能算数」。
A2 不依赖公网地址、不需要外部确认，**现在就能做**；做完之后 A1 只是把
`ApprovalPort` 换成一个新适配器。

**A2 交付判据**：审批人必须是可验证身份（GitHub login / Feishu open_id），
必须属于白名单，必须 ≠ 推送者；不满足时 fail-closed 并写进审计记录。
终端通道要么接入同一套校验，要么在审计里显式标记为「未验证身份」。

**A1 交付判据**：审批发生在推送者的机器之外——第三个人也能批。

> **替代通道建议**：`ApprovalPort` 已经是抽象端口，第一版远程审批不必是飞书。
> 「允许名单内的 GitHub login 在 PR 上评论 `APPROVE <bundle_hash>`，经 GitHub API
> 回读校验」可以**完全绕开公网地址**：GitHub 的轮询/事件走的是 GitHub 自己的通道，
> 不需要 funnel、不需要 8083、不需要和 nexus-vibe 抢地址。飞书保留为可选适配器。

### B. 执行体可靠性层 —— 决定体验，但不靠写代码解决

现状：21 条实测用例 `contract_passed` ≈ 48%；8 条 budget 耗尽**全部**是
`read_file` 循环；工具轮次上限已有界；`delivery resume --run-id` 已存在（`app/cli.py:715`）。

缺口不是「模型不行」，而是：

1. **探索预算与写入预算未分离** —— 读文件循环把整单的轮次吃光，然后以
   「预算耗尽」这种无信息量的理由失败；
2. **失败态不可续跑的可发现性** —— 有 `resume`，但没有「失败 → 一键续跑」的产品路径
   （CLI 已有 `--run-id`，缺的是把 run_id 和可续跑性直接摆在人面前）；
3. 强模型批次要等真实付费额度，**立新协议，不预置开发**。

**交付判据**：受控用例集上，每一单要么完成、要么落到**已分类且可续跑**的状态；
「预算耗尽」必须带上是哪类工具吃掉的。

### C. 评测仪器层 —— 对外宣称的唯一合法来源

issue #95 第 2–4 步：24 条策展用例、协议注册、多轮分布 + 置信区间。
在这之前，任何「通过率」都是单点读数，只能内部看，不能对外说。

**交付判据**：仓库内可复现的报告产物——n≥3 轮、逐例结果向量、区间；
第三个人 clone 下来能重跑出同样的结论形状。

**状态**：多轮评测仪器与预注册已交付（`eval/aggregate.py`、`scripts/eval_report.py`、
`run_eval_baseline.py --rounds`、`eval-multiround-preregistration.md`）；3 轮实跑待所有者
批准后补。

### D. 通用性层 —— 跨仓

现状：`delivery run/preflight/ci-triage` 都有 `--repo`（`app/cli.py:826,860,874`），
但验证命令是**全局环境变量**（`CODE_REVIEW_VERIFY_COMMAND` / `CHANGE_AGENT_VERIFY_COMMAND`，
`app/config.py:238,266`），没有 per-repo 的仓库档案。

缺口：换一个仓库 = 换一套验证命令、允许路径、分支保护假设，现在只能改环境变量重跑，
**这恰恰是第二个人没法用的地方**。

**交付判据**：在自己的第二个真实仓库上跑 1–2 单，把仓库档案（verify command、
allowed paths、分支保护假设）固化成一份**配置契约**（而非环境变量），
PR 里附上该仓库自己的 CI 绿灯。不需要「别人」。

**状态**：配置契约已交付（per-repo 仓库档案，PR #107）；第二个真实仓库实跑 1–2 单待补。

### E. 部署层 —— 私有化 runbook

不做 hosted。`compose` + `doctor` 已有，缺「新用户从 clone 到第一单」的路径：
一份文档 + 一个脚本，外加 headless/server 模式（**依赖 A1**，本地 TTY 审批在服务器上没有意义）。

**交付判据**：一台干净机器（或干净容器）照文档 + 脚本走到第一个已合并的 PR。

### F. 治理完整性 —— 收尾级，已在计划内

- P1 契约（PR #104）、ADR-039 BLE001、PR #71 —— 进行中/待签收；
- 台账自写守卫（基线 §3.1）：目前只有人拦，应与 A2 的身份底座一起做；
- **OTel：要么补齐，要么删宣称。** 二选一，不许悬着。

## 2. 路线图

```
阶段 0（已在跑，无外部依赖）
  #104 签收 → 合并 → ADR-039 BLE001 → PR #71 收尾
      │
阶段 1（通用性核心，无外部依赖）
  A2 身份模型：Approver ≠ Operator，白名单统一，fail-closed 写审计
      │
      ├── D 仓库档案契约 + 在自己的第二个仓库实测 1–2 单
      │
阶段 2（证据）
  C 多轮评测仪器（#95 第 2–4 步）—— 从此才允许谈「通过率」
      │
阶段 3（渠道 + 部署）
  A1 远程审批（GitHub 原生评论优先，飞书可选）→ E headless runbook + 一键脚本
      │
阶段 4（体验）
  B 探索/写入预算分离 + 失败→一键续跑；强模型批次等付费额度另立协议
      │
阶段 5（收尾）
  台账自写守卫（复用 A2 身份底座）、OTel 补齐或删宣称
```

**为什么这么排（与原始清单的三处差异）**：

1. **A2 提到 A1 前面**：身份模型是 A1 的地基，且不被外部依赖卡住。原始清单把两者
   并列为「A」，实际执行时 A2 可以先走。
2. **D 提到 C 前面**：跨仓实测暴露的是「配置契约」问题，不改代码就能发现；
   它比多轮评测更能直接回答「别人能不能用」。两者不改同一批文件，也可以并行。
3. **A1 优先 GitHub 原生通道**：如果坚持飞书，第一版远程审批就被 nexus-vibe 的
   地址争议卡住；GitHub 评论审批把这个外部依赖整个消掉。飞书作为第二适配器。

**每阶段的硬门槛**（不过门槛不许进下一阶段）：

| 阶段 | 门槛 |
|---|---|
| 0 | 三项全合并、CI 绿、台账无 Escape |
| 1 | 一段演示：两个不同身份完成一单，审批人 ≠ 推送者；自审批被拒且有审计记录 |
| 2 | 第 2 个仓库走完整链路并合并一单，仓库档案来自配置文件而非环境变量 |
| 3 | n≥3 轮评测报告入库，区间可复现 |
| 4 | 一人不在你机器前，完成审批 → 合并；干净机器照文档跑到第一单 |
| 5 | 每一单失败都有分类与续跑路径；OTel 二选一有结论 |
